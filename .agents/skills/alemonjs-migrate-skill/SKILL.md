# AlemonJS 迁移技能

目标：把旧插件项目或混合项目迁移成 alemonjs 应用结构。该技能不负责一般 alemonjs 日常开发，专门处理“读取旧结构并重建到新结构”的工作。

补充原则：迁移的目标不是长期兼容旧项目目录。迁移完成后，旧 `plugins/**`、旧配置文件、旧资源文件、旧运行数据文件默认都视为待废弃内容；它们可以作为短期导入源，但最终应从正常运行链路里移除，必要时直接删除。

## 迁移后必须继续做的内容

迁移不等于“命令能跑”。迁移完成后，默认还要继续收口以下内容，直到它们符合 alemonjs 约定：

1. 默认资源收口
   默认 YAML / JSON / 帮助资源要改成编译器 import
   例如：
   `import configDefault from './config_default.yaml'`

2. 配置收口
   默认值在代码或编译期资源里
   生效配置在 Redis / 存储层
   不能把项目根 `config/**` 当成最终设计

3. 数据收口
   运行时 key 统一改成 `data:AppName:*`
   配置类 key 优先 `.yaml`
   状态类 key 优先 `.json`

4. 路径收口
   业务模型里不再直接拼旧插件路径
   旧目录结构只能存在于迁移层 / 兼容层
   不要继续保留通用 `appPaths` 一类目录管理器

5. 路由收口
   旧正则匹配、旧命令分发要尽量迁到 `Router.create().group().use()`
   handler 不再重复解析命令文本

6. 模块收口
   已迁成应用能力的模块要改成“应用内建模块”或应用自有模块
   不再依赖旧模块目录作为主来源

7. 存储兼容收口
   旧 Redis key、旧本地 fallback 文件、旧 YAML 配置目录都应下沉到统一迁移层
   正常读写链路不再直接接触旧结构
   legacy 导入优先做成显式迁移动作，不要默认挂在正常启动链
   迁移完成后，这些 legacy 入口本身也应继续删除，不保留为长期兼容层

8. 平替验收
   不只看“有没有命令”
   还要看：
   功能是否完整
   表现是否对齐
   配置是否脱文件
   存储是否已统一
   legacy 依赖是否已经脱离

## 迁移完成度分层

迁移默认按下面四层汇报，不允许把“第一层能跑”误报成“完全迁完”：

- 核心可用
  命令能命中，服务能跑，至少文本版可用
- 表现迁移
  图片卡片、帮助页、展示型能力迁完
- 结构解耦
  默认资源、配置、存储、路由、模块来源都切到 alemonjs 主结构
- 完整平替
  功能、表现、存储、配置、模块管理都不再依赖旧项目

## 迁移技能的职责边界

以下内容属于迁移技能：

- 读取 `plugins/**`、`apps/*.js`、`model/*.js`、`utils/*.js`、`config/**`
- 建立旧命令到新 `src/router.ts` / `src/response/*.ts` / `src/model/*.ts` 的映射
- 把 legacy 配置、legacy 目录、legacy key 收口到专门迁移层
- 明确声明旧项目目录和旧文件只是短期导入源，迁移完成后应废弃或删除
- 在迁移后继续做解耦，而不是停在“表面可用”

以下内容不属于迁移技能，而属于 alemonjs 通用开发技能：

- alemonjs 路由 DSL 的一般规范
- lvyjs 默认资源导入约定
- 统一数据 key 命名规范
- 通用消息格式、Hook、Format、运行时配置原则

## 迁移后的默认检查表

每次迁移一个模块或能力后，默认检查：

- 默认资源是否已经改成 direct import
- 业务层是否还在 `path.join()` 拼默认文件
- 生效配置是否仍依赖项目文件目录
- store key 是否已统一为 `data:AppName:*`
- handler 是否还在自己二次匹配命令
- 是否仍直接读取 `plugins/旧项目/**`
- 模块是否已从“旧目录兼容”升级为“应用内建 / 应用自有”

只要上述任一项还没完成，就不能宣称迁移已经结束。

## 本次迁移经验

本类项目在迁移过程中，容易出现以下误区，后续迁移默认避免：

- 误区 1：把“命令已经可用”当成“迁移已经完成”
  正确做法：
  继续检查配置、存储、默认资源、legacy 目录依赖、模块来源

- 误区 2：把项目根 `config/**` 当最终配置方案
  正确做法：
  只把它作为中间态或迁移导入源
  最终仍应收口到 Redis / 存储层

- 误区 3：迁移后继续在业务层使用 `path.join()` 拼默认资源或旧插件路径
  正确做法：
  默认资源交给编译器 import
  旧目录兼容收进迁移层

- 误区 4：迁移后保留“模块下载 / Git 更新 / 仓库管理”语义
  正确做法：
  先判断当前应用是不是管理型应用
  如果只是功能服务型应用，应下线这些能力或改成边界提示

- 误区 5：旧 key、新 key、旧回退文件、新回退文件同时散落在业务模型里
  正确做法：
  统一下沉到存储层或迁移层
  业务模型只保留 store key 与数据结构

- 误区 6：把 legacy 配置导入挂在正常启动逻辑里
  正确做法：
  改成显式迁移命令或一次性迁移任务
  让正常运行态不再主动触碰旧项目目录

- 误区 7：把 `plugins/**` 和旧配置文件当成需要长期保留的兼容层
  正确做法：
  把它们只当迁移导入源
  迁移完成后继续删除 legacy 目录、legacy 文件和 legacy 入口

- 误区 8：迁移 skill 和 dev skill 职责混杂

  正确做法：
  alemonjs 通用约定写进 dev skill
  迁移后继续收口的内容写进 migrate skill

## 可复用迁移差异模型

迁移 Yunzai 插件时，优先提炼三类差异，而不是只记录“这个插件做了哪些功能”。
后续迁移其他插件时，默认先按下面三层分析并收口。

### 1. 代码实现差异

旧 Yunzai 插件常见特征：

- 命令识别和业务逻辑混在同一个 handler
- handler 直接读取整条消息文本，再手写正则分支
- 事件对象一路向下透传到 model，model 也依赖聊天框架字段
- 配置、资源、运行数据在业务代码里顺手读取
- 一个文件同时负责命令识别、参数解析、请求、格式化输出

迁移到 alemonjs 后，默认目标是：

- Router 负责命令命中，handler 不再负责识别自己是哪条命令
- `useRoute()` 负责读取 `key / params / rawArgs`
- `useEvent({ selects })` 只负责事件能力声明和真实事件上下文
- model 层优先接收明确参数，而不是整条消息文本
- response 只负责编排和输出，model 才负责业务计算
- 图片渲染独立到 `img/views`，不和业务逻辑混写

迁移检查：

- 是否仍在 handler 里手写正则分支判断命令
- 是否仍把整条消息文本传到 model 再二次解析
- 是否仍把事件对象当成所有 model 的通用输入
- 是否已经把命令识别、参数解析、业务计算、展示输出拆开

### 2. 存储差异

旧 Yunzai 插件常见特征：

- `config/*.yaml`、`data/*.json`、`resources/*` 作为主设计
- 默认配置、用户配置、运行状态、缓存数据都混在文件系统
- 配置修改默认等于改文件

迁移到 alemonjs 后，默认目标是：

- 默认值属于编译期资源，不属于运行时主配置
- 生效配置走 Redis / 存储层
- 本地文件最多只作为 fallback 副本，不是主设计
- store key 统一使用 `data:AppName:*`
- key 可以携带格式语义，如 `.yaml` / `.json`
- 旧目录、旧文件、旧 key 只允许作为短期迁移导入源

迁移检查：

- 默认资源是否已经 direct import
- 生效配置是否还依赖项目文件目录
- 运行状态是否仍直接写旧 `data/*.json`
- store key 是否已统一
- legacy 文件和 legacy key 是否只存在于迁移层

### 3. 设计理念差异

旧 Yunzai 插件常见特征：

- 插件寄生在宿主目录结构上运行
- 宿主目录结构本身就是系统边界
- 配置文件就是产品入口
- 插件容易顺手承担很多附带职责

迁移到 alemonjs 后，默认目标是：

- 迁移结果是独立应用，不是旧目录脚本
- 路由、状态、资源、展示都要有明确边界
- 功能服务型应用只做功能服务，不做仓库管理或模块市场管理
- legacy 兼容是过渡，不是长期架构
- 编译器和框架能力优先于手写路径、手写目录约定、手写脚本式心智

迁移检查：

- 是否还把旧目录当运行时主来源
- 是否还把项目根 `config/**` 当最终设计
- 是否还保留不属于功能服务型应用的管理职责
- 是否把 legacy 兼容当成了长期方案
- 是否在迁移完成后继续删除 legacy 入口本身

## 迁移技能的通用结论

迁移 Yunzai 插件时，要把：

- 目录驱动
- 文件驱动
- 消息文本驱动

改造成：

- 路由驱动
- 存储驱动
- 参数驱动

如果迁移结果仍然主要依赖旧目录、旧文件、整条消息文本和脚本式分支，那么它还停留在“旧插件换了个目录”，不算真正迁成 alemonjs 应用。

## 迁移判定模板

迁移其他 Yunzai 插件时，默认不要直接开始改代码。
先按下面模板输出一次判定，再进入实现。

### A. 插件定位判定

先判断旧插件本质上属于哪一类：

- 功能服务型应用
- 管理型应用
- 图鉴 / 资料型应用
- 订阅 / 推送型应用
- 混合型应用

必须先写清楚：

- 它真正对外提供什么能力
- 哪些能力是主能力
- 哪些能力只是旧宿主生态附带出来的次要能力

如果定位都没分清，不要直接沿用旧目录结构和旧模块心智。

### B. 代码实现判定

必须列出下面四项：

- 命令识别现在在哪里做
- 参数解析现在在哪里做
- 业务计算现在在哪里做
- 输出渲染现在在哪里做

并明确判断：

- 是否仍然是整条消息文本驱动
- 是否仍然是 handler 混合命令判断和业务执行
- model 是否仍依赖事件对象而不是明确参数
- 图片渲染是否和业务逻辑混写

结论必须明确写成：

- 可直接保留的实现
- 必须迁到 Router 的实现
- 必须改成 `useRoute()` 的实现
- 必须继续保留 `useEvent({ selects })` 的实现

### C. 存储与资源判定

必须列出下面四类资源分别在哪里：

- 默认配置
- 用户配置
- 运行状态
- 静态资源 / 帮助资源 / 数据表

并明确判断：

- 哪些应该 direct import
- 哪些应该进入 store
- 哪些只是一次性迁移源
- 哪些迁完后应删除

结论必须明确写成：

- 编译期资源
- 运行期配置
- 运行期状态
- legacy 导入源

### D. 设计理念判定

必须明确判断下面几点：

- 这个插件迁完后应该是独立应用，还是应用内某个能力模块
- 它是否真的需要模块管理、仓库管理、目录扫描、配置文件入口
- 它是否仍然依赖旧宿主目录结构作为系统边界
- 它是否存在不属于功能服务型应用的管理型职责

结论必须明确写成：

- 应保留的应用职责
- 应删除的旧宿主职责
- 应下沉到迁移层的 legacy 职责

### E. 输出格式要求

每次迁移分析默认按下面结构输出：

1. 旧插件实际在实现什么
2. 旧插件的主能力与次能力
3. 代码实现上的旧模式与新目标
4. 存储上的旧模式与新目标
5. 设计理念上的旧模式与新目标
6. 哪些可先迁，哪些必须后删
7. 当前迁移完成度属于：
   - 核心可用
   - 表现迁移
   - 结构解耦
   - 完整平替

没有先做这份判定，就不要直接把旧插件代码原样搬进 `src/**`。

## 迁移后的推荐收尾顺序

每次从旧插件迁完一个能力后，默认按这个顺序继续收尾：

1. 让命令可用
2. 把路由命中上提到 Router
3. 把默认资源改成 direct import
4. 把配置切到存储层
5. 把 store key 统一成 `data:AppName:*`
6. 把旧 key / 旧文件 / 旧目录兼容压到单独迁移层
7. 把模块语义从“兼容模块”升级成“内建能力”
8. 清理不属于功能服务型应用的管理职责
9. 删除已经不再需要的旧目录、旧文件和 legacy 入口
